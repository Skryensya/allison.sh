## La idea

Skryensya/ui es un sistema de diseño contract-first. En vez de tratar los componentes como piezas de CSS y JavaScript envueltas en una API, cada componente parte de una definición, llamada su contrato: qué partes tiene, qué opciones acepta, qué atributos escribe, qué reglas de accesibilidad debe cumplir y qué combinaciones tienen sentido.

El problema que intenta resolver es concreto. En sistemas institucionales, lo normal es ordenar el caos definiendo un stack único para todos los proveedores. Tiene sentido: baja la variación y facilita mantener una línea común. Pero también fuerza una decisión técnica sobre equipos que no siempre parten desde el mismo lugar, reduce el grupo de proveedores posibles y sube el costo para la institución. A mí me interesaba resolver esa tensión de otra forma: permitir React, Vue o Vanilla sin convertir el sistema en tres implementaciones paralelas.

La idea viene de lo que aprendí creando y manteniendo sistemas de diseño en producción: el <a href="/proyectos/kit-digital-uc" class="editorial-link">Kit Digital UC</a>, el Portal UC y un proyecto institucional reciente que todavía no puedo mostrar. <a href="https://zagjs.com" class="editorial-link" target="_blank" rel="noopener noreferrer">Zag.js</a> fue la puerta de entrada técnica: separar comportamiento de presentación, trabajar con máquinas de estado y dejar que cada runtime pinte la misma lógica sin reinventarla.

## Lo interesante

En <a href="https://ui.skryensya.dev" class="editorial-link" target="_blank" rel="noopener noreferrer">ui.skryensya.dev</a> ya hay 100+ componentes documentados desde esa idea. Cada página muestra el contrato, las opciones, las notas de accesibilidad y ejemplos renderizados. React y Vanilla no existen como promesa futura: ya son dos implementaciones que tienen que producir el mismo resultado a partir de la misma definición.

La parte importante no es solo tener muchos componentes. Es que el catálogo se puede consultar como estructura mediante un MCP server. Desde ahí se puede preguntar qué componentes existen, cómo se componen, qué combinaciones son válidas y qué markup deberían producir. Las validaciones comparan árboles de uso entre bindings y convierten “esto debería ser consistente” en evidencia.

## Estado actual

Es un WIP grande y deliberadamente ambicioso, pero ya tiene una base funcionando: Core como fuente de verdad, documentación pública, implementaciones en React y Vanilla, y gates que revisan consistencia. Lo siguiente es aprovechar esa misma estructura para cosas que normalmente se construyen aparte: un plugin para Figma, un editor visual y un MCP que valide interfaces de manera programática.
